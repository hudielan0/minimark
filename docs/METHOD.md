# MiniMark 方法论学习记录

MiniMark 有两个同等重要的交付物：一个可靠的 Markdown 产品，以及一套可以迁移到其他项目的 AI 产品开发方法。

## 我们的分工

- AI 负责：检索事实、拆解风险、提出可证伪问题、实现最小实验、运行测试、暴露失败和整理证据。
- 人负责：判断产品方向、批准测试边界、权衡取舍、验收可见行为，以及决定是否提交或发布。
- 共同负责：把真实失败沉淀为测试、规则、技能或发布门槛，而不是只留在聊天记录里。

## 每个检查点必须同时交付

1. 产品结果：这一次具体做成了什么。
2. 验证证据：自动测试、手工验收和失败记录。
3. 方法卡：发现了什么、为什么这样做、否决了什么、剩余什么风险。
4. 可复用步骤：换一个产品时，哪些步骤可以原样执行。
5. 人类判断题：哪些选择不能由 AI 擅自决定。

## Phase 1 方法卡：先消除风险，再建设产品

### 发现了什么

- “轻量编辑器”首先是信任问题，而不是界面问题。最危险的是内容丢失、覆盖外部修改、崩溃后无法恢复，以及预览执行不安全内容。
- 技术名称不是结论。只有在真实开发环境中完成编译、文件选择、保存和恢复，才能暂时接受一个技术栈。
- 单个模块测试通过还不够。必须再用一层很薄的桌面壳把模块串成用户能走完的路径。
- 正常案例只能证明它会工作；故意制造外部修改，才能证明它在冲突时不会做危险的事。

### 为什么这样做

如果先写完整界面，最晚才发现保存机制或桌面框架不合适，前面的代码会变成负担。风险实验把最不确定、损失最大的假设提前，用最少代码换取决策证据。

### 本阶段执行顺序

1. 从产品承诺中提取不可违反的边界。
2. 把未知项写成能被实验推翻的问题。
3. 先写失败测试，证明当前能力不存在。
4. 只实现让测试通过的最小机制。
5. 把独立机制接进一个薄桌面壳。
6. 走正常案例、边缘案例和故意刁难案例。
7. 分开记录已验证事实、临时判断和未解决风险。
8. 由人验收后，才提交和公开。

### 已形成的证据

- 四个保存与恢复测试通过。
- 两个 Markdown 预览安全测试通过。
- macOS 应用能够打开文件、实时预览、写恢复草稿并安全保存。
- 人为让外部程序修改文件后，应用拒绝覆盖，外部版本得到保留。
- `.app` 已生成；`.dmg` 封装仍失败，因此不能宣称“可以发布”。

### 可迁移到其他项目的模板

```text
产品假设
→ 用户不可承受的失败
→ 风险按“损失 × 不确定性”排序
→ 为最高风险定义公开验证接口
→ 失败测试
→ 最小实现
→ 薄的端到端路径
→ 正常 / 边缘 / 对抗案例
→ 决策记录与未决风险
→ 人类验收
→ 提交发布
```

### 仍需人判断

- Tauri 的轻量优势是否值得承担 Rust 和平台打包成本。
- 第一版是否允许远程图片；这会改变“内容完全本地”的边界。
- 当前仍存在很小的同时写入竞态，第一版要继续加固还是先用明确提示约束使用场景。

## 下一检查点

Phase 2 不继续扩张功能，只把实验代码整理成一个清晰的正式纵向切片：打开一个文件、编辑、预览、保存。验收时重点判断操作是否足够简单，而不是代码数量是否足够多。
